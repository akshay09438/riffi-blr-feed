# Technical spec - Riffi ingestion engine

*How the engine is built. Status on 5 Oct 2026: **steps 1-7 built** (the AI pass excepted), plus step 8's digest and health report - the fetchers, cleaning, stories, keyword tagging, scoring, the database, the CLI, the scheduler and the digest are as-built (the sections marked "as built" below); the dashboard, `/api/stories`, AI pass, exclusions and recall test are still the target design from `BRIEF.md` and `DECISIONS.md`. Rewrite each section to "as-built" in the same change that builds it.*

## Stack

- Python 3.11 (ARM64 on the founder's laptop: `py -V:3.11-arm64`), one virtual environment in `.venv/`.
- SQLite for phase 1 (`data/engine.db`), written so it can move to Postgres later.
- Fetching: httpx. Parsing: feedparser (RSS/Atom, YouTube Atom); Python's own `html.parser` for Telegram's public channel pages (`fetchers/telegram.py`, D-011). Page text: trafilatura.
- De-duplication: RapidFuzz (`token_set_ratio >= 85` within 48 h).
- Scheduling: Windows Task Scheduler runs `fetch --due` every 30 min (D-008); no scheduler library. CLI: Typer. Dashboard and `/api/stories`: FastAPI, bound to `127.0.0.1` (D-003).
- AI tagging: a Claude Code session on the founder's plan, through files (D-005). No Anthropic API key.
- Tooling: pytest (+ pytest-cov), ruff (lint + format). No type checker. `tests/conftest.py` points `RIFFI_DB_PATH` at a temporary file for every test, so a test that forgets `--db` can never write into `data/engine.db`.

## Fetchers (as built, 4 Oct 2026)

- `fetchers/http.py` - `PoliteClient`, the only way the engine touches the network. Browser User-Agent (D-004); one request at a time per domain and 2-2.5 s between request starts on a domain (other domains run in parallel); 20 s read timeout plus a 60 s overall deadline; 2 retries with 2 s / 4 s backoff on network errors, 429 (Retry-After, capped at 30 s) and 5xx, none on DNS/TLS failures; redirects followed by hand (up to 10) so every hop goes through its own domain's gate; X, Instagram and WhatsApp are refused even when a redirect points there; a domain that fails 3 times in a row at network level (timeout, DNS, connect) is skipped for the rest of the run; conditional GET (ETag / Last-Modified in, 304 reported as "not modified"); 15 MB cap; TLS always verified, against the operating system's trust store through `truststore` (`tls_context()`, D-010: on Windows the browser's store, which fetches an intermediate certificate a site forgot to send). Never raises for a network problem - the result carries the error.
- `fetchers/parse.py` - feedparser (fed a `BytesIO`) into `Entry` (title, link, published in UTC, summary stripped of HTML and cut to 1,000 chars, author, image from media:content / media:thumbnail / enclosure / first `<img>`, Google News `<source>`, guid). Dates that carry no zone (and "... IST") are read as IST, since every source that omits the zone is Indian; feedparser alone would read them as UTC (5.5 h off) and misread `29-09-2026` as 2029. `looks_like_html` catches feeds that answer 200 with a web page.
- `fetchers/feeds.py` - `plan()` decides per route what to fetch (table in the module); `fetch_source()` returns a `FetchOutcome` (`ok` / `not_modified` / `skipped` / `error`, reason, HTTP status, entries, validators) and never raises; `fetch_sources()` runs many at once. X/Instagram rows fetch only `backup_google_news_url` and are marked `on_backup`; `rss_app_url()` is the stub for the 5 `priority_x_feed` rows. Rows whose fetch_url is an instruction (S047, S107, S121), that lack a backup (S108), or whose backup is not a Google News feed are skipped with the reason.
- `fetchers/gnews.py` - `Resolver` turns Google News article links into publisher URLs: offline base64 decode first, else the two-request online decode (article page signature, then batchexecute); if Google redirects straight to the publisher, that URL is taken. Answers are cached by article id; online look-ups stop at 100 per run and the rest stay as Google News links for a later run. As built, `pipeline.run_fetch` loads the stored cache (`gnews_cache`), gives a `Resolver` to `clean`, and saves the new answers after the run (see "Pipeline and commands").
- `fetchers/pagemonitor.py` - the 19 web page monitors (S047 moved to Google News and S021 became a page monitor on 5 Oct 2026; S007, S015 and S041 moved to Google News the same day, D-013). GET with a browser Accept header; the first 1 MB of HTML goes to trafilatura in a worker thread with a 60 s limit (trafilatura takes ~6 s at 1 MB and minutes beyond, which would otherwise freeze every other fetch). Before extraction the page is pruned (5 Oct 2026, after S004/S109/S110/S048 all stored the same karnataka.gov.in Kannada privacy-policy text as their "main content"): `<noscript>` goes; so does any element whose id/class/role names a policy (`privacy`, `disclaimer`, `hyperlinking-policy`, `terms-of-use` / `terms-and-conditions`, `copyright-policy`, `website-policies`; bare "policy" is kept, since a "Policies" list is content), any hidden container (`hidden`, `aria-hidden="true"`, `display:none`, or a modal/popup/dialog/overlay class) whose first heading is a policy title, and a policy heading printed in the page (English or Kannada: Privacy Policy / ಗೌಪ್ಯತಾ ನೀತಿ, Disclaimer / ಹಕ್ಕು ನಿರಾಕರಣೆ, Terms of Use, Terms & Conditions, Hyperlinking Policy, Copyright Policy; the whole heading must be the title, so "Terms and conditions for tender No 17" stays) together with its following siblings up to the next heading of the same or higher level. Then main text with tables, or all visible text of the pruned page split into sentences when trafilatura finds no main text (or only a JavaScript notice). Lines that are only a "enable JavaScript" notice (160 chars max) are dropped. A page left with no lines (a JavaScript app shell such as S009 GBA and S008 ECI: "You need to enable JavaScript to run this app.") is an error, reason "the page needs JavaScript ...", which keeps the last snapshot and gets the health fix "this page needs JavaScript: find a different URL or a JSON endpoint" (`health.NEEDS_JS_FIX`, also used for a stored blank snapshot); no JavaScript is ever run. Stamp lines are dropped: a line with a stamp word ("updated", "reviewed", "visitors", "views", "sunrise", "rights reserved", "... ago") whose other words are only filler, dates, times and numbers, plus a bare date/time line straight after one. Lines with real words, Kannada text, or only numbers/dates without a stamp word (table rows, "Date: 15/10/2026") are content. The hash is over the *set* of lines, so reordering is not a change. Bot-check pages (Cloudflare "Just a moment...", "Access denied" titles, challenge markup) are errors. First visit: snapshot only, and no conditional-GET validators are sent until a snapshot exists. Later visits: a previous snapshot that never saw the page (only JavaScript notices, or policy wording sharing no line with the new text - taken before the pruning rules) is replaced as a new baseline with no entry; otherwise, if the hash changed, one entry - title = page `<title>` + " updated" (source name if none), link = the page, published = when the change was seen, summary = "Added: ... || Removed: ..." of lines that really changed (1,000 chars max), guid = source id + old hash + new hash. Every error (HTTP, non-HTML, bot check, extraction crash or timeout) hands back the previous snapshot unchanged. Snapshots go in and out on `FetchOutcome.snapshot`; storing them (page_snapshots) is step 6.
- Storing outcomes (fetch_runs, items, page_snapshots) and `test-feeds` came later: see "Pipeline and commands".

## Normalise and clean (as built, 4 Oct 2026)

- `normalise.py` - `clean(outcomes, sources, blocklist=, resolver=, now=)` turns every entry of every successful fetch into an `Item` (BRIEF.md items shape plus `canonical_url`, `url_resolved`, `on_backup`). Order matters: cheap drops first (no link, older than 7 days, blocklisted link or Google News `<source>` domain), then Google News links are resolved (so the per-run online cap is never spent on items about to be dropped), then the resolved URL is checked against the blocklist again. A Google News link that stays unresolved is kept only if its site is known (a `<source>` URL, or a source name that is a domain) and passed the blocklist; otherwise it is held back for a later run, so a copycat cannot slip through unresolved. One odd entry (unreadable URL, missing fields, unknown source) is dropped with its reason, never stops the run. Dates missing or more than 6 h ahead become the fetch time; `published_at` / `fetched_at` are stored in IST. Publisher: Google News `<source>`, the channel name for Telegram and YouTube, otherwise the source name. Title: " - Publisher" stripped for Google News; a Telegram post with no title gets its first sentence. Language by script: `kn` when at least 30% of the letters are Kannada, `other` when another script dominates, else `en`. `canonical_url` (https, no amp/mobile variants, no tracking parameters) gives `item_id` = sha256; Google News items are keyed on Google's article id instead, so a link stored unresolved and resolved later stays one item. Every drop is counted by reason in `CleanResult.dropped`. Cricket match-record pages are a cheap drop too ("match record page (scorecard/commentary/squads/highlights)"): a title that names a match ("A vs B") and either ends in " - Scorecard / Squads / Commentary / Live Score / Live Cricket Score ..." (optionally followed by one " - Publisher" segment) or is a "Highlights: A vs B | TATA IPL ..." video, because Google News re-dates old Cricbuzz pages past the 7-day check; a season year alone never drops a title, and the page names live in `MATCH_PAGE_NAMES` / `HIGHLIGHT_LEAGUES` in `normalise.py`. Excluded-topic dropping needs topic tags (step 4).
- `safety/blocklist.py` - reads `blocklist.csv` generously: every domain in the `name` and `url` columns counts (rows list several, joined by " / "), a URL with a path blocks only that path (one X account, not all of X), a domain covers its subdomains; words that only look like domains ("notice.pdf", "Node.js") are ignored. Matching reads a link the way a browser does (case, trailing dot, port, user-info, backslashes, full-width dots), checks AMP copies (google.com/amp/s/..., *.cdn.ampproject.org) as the page they copy, treats twitter.com as x.com, compares paths decoded and without doubled slashes, and never raises. Not handled: link shorteners (t.co, bit.ly) are not followed. Rows with no domain in them are reported in `Blocklist.problems` for a person to fix, never guessed (none today; the two such rows got their domains on 4 Oct 2026).

## De-duplicate into story clusters (as built, 4 Oct 2026; matching form 5 Oct 2026)

- `dedupe.py` - `Clusterer` groups items into stories. Same `item_id` = same item, stored once. Otherwise an item joins the story whose title matches best, if it was published within 48 h of that story's *first* report (so recurring items like "Gold rate today" start a new story instead of chaining forever). A match needs all three: rapidfuzz `token_set_ratio` >= 85 on normalised titles (BRIEF.md); no conflicting detail (two different sets of numbers, or a word on each side with no near-match on the other, e.g. BJP/Congress, Delhi/Bengaluru, today/tomorrow - "floats"/"floated" are near-matches at `ratio` >= 75); and the shorter title has >= 70% as many meaningful words as the longer (so "Metro fare hike" cannot swallow "Metro fare hike rolled back"). `token_set_ratio` alone scores 100 whenever one title's words sit inside another, which the last two rules stop. The rules were chosen on labelled Bengaluru headline pairs kept in `tests/test_dedupe.py` (all same-story pairs merge, no different-story pair does) - add pairs there when a live run shows a mistake. All three rules compare titles in a *matching form* (5 Oct 2026, after one live story split into three): dates written one way ("October 3" = "3 October" = "Oct 3rd" -> `10-03`; two different dates conflict like two different numbers; day-first "3 May" is not read as a date), "Bangalore" -> "Bengaluru", stop-words dropped, light stemming of plain English words ("extends"/"extended" -> "extend", "timings" -> "tim"), and "Bengaluru" dropped from, and counted as said by, a title naming a Bengaluru-only body (Namma Metro, BBMP, BMTC, BMRCL, BWSSB, BESCOM, BDA) - so "... in Bengaluru" no longer reads as a conflicting detail against a Namma Metro title, while "Delhi" vs "Bengaluru" still does. The same story in other words ("services to run beyond midnight" vs "timings extended") still splits: title matching cannot join it without also joining "Namma Metro fare hike from October 3"; those pairs are kept as strict expected failures (`KNOWN_SPLITS`) and left to the AI pass. A trailing " - Publisher" / " | Publisher" is ignored when comparing. Page-monitor items never join stories by title. A story keeps every member; `headline` = the earliest report, `first_seen_at`, `started_at`, `sources`, `source_count` (distinct sources, drives scoring) and `publisher_count`. Earlier stories (step 6: the last 48 h from the database) are passed in as `existing`. Speed: candidates come from one rapidfuzz bulk scan, each distinct title is stored once per story; 200 new items against 16,000 stored take about 5 s, 5,000 fresh items about 1.5 s.
- `normalise.py` - page-monitor items get `item_id` from the page URL plus the change's guid, since every change of one page has the same URL. `norm_title` keeps combining marks, so Kannada vowel signs no longer split words into fragments.

## Tagging, keyword pass (as built, 4 Oct 2026)

- `config/topic_keywords.yaml` - team-editable: for each of the 151 topics a label and 5-15 plain keyword phrases (1,904 in all, drafted by Claude from each topic's title and debate angles on 4 Oct 2026), optional `local: true` (64 topics) and optional `exclude` phrases; plus the `local_context` list of place and body names. The header explains the rules for editors.
- `tagging/keywords.py` - `KeywordTagger.load(path)`; `tag(text)` / `tag_texts([...])` return `TagResult(topics={topic_id: [matched keywords]}, local, unmatched_local)`. Matching is case-insensitive; English keywords match whole words only; Kannada keywords match at a word start (suffixes allowed; `\b` does not work in Kannada script); keywords are plain text, never regexes; the longest keyword at a position is reported. A story is tagged from all its members' titles and summaries at once. `local: true` topics need a `local_context` name somewhere in the story; `exclude` vetoes. This pass favours recall - the AI pass (step 4, part 2) confirms or rejects candidates. `unmatched_local` = names Bengaluru/Karnataka but matches no topic (BRIEF.md: weekly human review). `check_against_topics_csv` lists topics.csv ids without keywords and vice versa (a test keeps it empty).

## Pipeline and commands (as built, 4 Oct 2026)

- `fetchers/feeds.fetch_sources` runs different sites in parallel but each site's sources one after another, and Google News look-ups run one at a time: the client counts a request's 60 s limit from when it starts waiting its turn, so queueing all 84 Google News feeds at once would time most of them out unsent (found in review; a test reproduces it).
- `pipeline.run_fetch(conn, sources)` - one cycle: load conditional-GET validators, page snapshots and the Google News cache from the database; fetch; clean (incl. Google News resolution); drop items already stored; group into stories against the last 48 h of stories; save items and stories in one transaction; then record every fetch's health, validators and page snapshots (after the items, so a crash between the two only means re-reading those feeds next time, never losing items); tag each touched story from all its stored reports; save new Google News resolutions; prune (D-002). Returns a `RunSummary` (statuses, entries, new items, drops by reason, entries already stored by an earlier run, entries repeated within this run (so entries = new + dropped + already stored + repeated), new / grown stories, tagged, unmatched local, Google News look-ups).
- `health.check(outcome, now)` - BRIEF.md checks Reachable / Valid / Alive (7 days) / Fields (title, link, date; fields are judged as cleaning will see them, so a Telegram post's text counts as its title - cleaning takes its first sentence) with a suggested fix per failure (wrong URL, blocks bots, t.me or rsshub.app refusing vs channel not found or not public, needs a channel ID or backup URL, page-not-feed, Google News query empty, a monitored page with no readable text, and per missing field: no title, no link - every entry dropped - or no date - dated at fetch time). "Useful" needs history and belongs to the daily report.
- `cli.py` (Typer; `python -m riffi_ingest`): `import-sources`, `import-topics`, `test-feeds` (stores nothing; prints the table and writes `reports/test-feeds/<YYYY-MM-DD-HHMMSS IST>.csv/.md`, with `-2`, `-3` ... added if that name is taken, so runs never overwrite each other), `fetch --all | --source ID` (imports sources on the first run; one fetch at a time via an OS file lock beside the database; a progress line per source and a time estimate; clear errors for unknown ids, `--all` with `--source`, or a missing feeds.csv; console output never crashes on characters the console cannot show). Default paths are anchored on the project folder. `fetch --due`, `status` and the run diary came on 5 Oct 2026 (see "Scheduler"). `digest` and `report` came with step 8 (see "Outputs").

## Scoring (as built, 4 Oct 2026)

- `config/scoring.yaml` - team-editable weights: the BRIEF.md table exactly (priority 30/20/10, geography 25/20/12/10, new development 15, debate angle 10, sources 3+/2/1 = 10/5/0, tier Official/Media/Aggregator = 10/6/3) and labels (High 70+, Medium 45+, Low 20+, else Drop). Mapping of the CSVs' richer values: geography = the first place named ("Pan-India (Bangalore angle)" = Pan-India; Bangalore = Bengaluru; Tamil Nadu = South India); tier = the word before any bracket ("Media (Kannada)" = Media), with Fact-checker / Research / Civic org / Union scored as Media (6). A test checks every real geography and tier value maps to points.
- `scoring.py` - `Scorer.score(StoryFacts)` -> total, label, sensitive, awaiting_ai, per-factor parts, best topic. A story scores by its best topic (priority + geography); the best source tier among its sources counts. Excluded -> Drop regardless (step 4 part 2); a topic with a `sensitive_note` sets the sensitive flag but keeps the score. Without the AI pass the AI points are 0 and `awaiting_ai` is true (open question 1): the highest score possible is then 75, so High needs a High-priority Bengaluru topic with 2+ sources and an Official source, or 3+ sources.
- `db/store.py` - `story_facts` (topics: the AI's when present, else keyword; tiers of the story's distinct sources), `save_score` (relevance_score, label, sensitive), `top_stories`.
- Run: every story touched by a run is re-scored after tagging. CLI: `stories [--top 30] [--hours 24] [--label High]` lists the best stories (score, label, sources, topics, headline, [sensitive], [awaiting AI]) - the brief's first-run "top 30". The first `fetch` imports topics.csv too; a run without topics stops with a clear message (every story would otherwise score Drop).

## Scheduler (as built, 5 Oct 2026)

Why it exists: the two-week test needs 14 days of unattended fetching where every gap has a known cause (laptop asleep, no internet, a crash, or the source itself). D-008 records the departures from the brief.

- **Speeds** - `config/schedule.yaml`, read by `scheduler.py` (`Schedule.load`, `interval`, `problems`, `due`) on every run. A speed is `<n>m`, `<n>h` or `never`; a bad value stops the run with a message naming the file. One speed per `route_type` (Telegram 30m; Google News, the X/Instagram backups, publisher RSS/Atom and YouTube 2h; page monitors 6h; Manual never), plus `sources:` overrides by id, which beat the route's speed. `early_minutes: 5` makes a source due that much before its interval is up, so timer jitter never costs a whole beat; it must be a whole number from 0 to 29, and anything else stops the run with a message naming the file. Nothing can run faster than the timer's 30-minute beat. `Schedule.problems` names any route type with no speed (its sources would never be fetched) and any override for an unknown or inactive source; `fetch --due` and `status` print these as warnings, and a test checks the real file against the real `feeds.csv`.
- **The timer** - `scripts/schedule-windows.ps1` registers one task, "Riffi ingestion engine - fetch": `.venv\Scripts\pythonw.exe -m riffi_ingest fetch --due` from the project folder (no window), first at the next :00 or :30 and then every 30 minutes with no end date. It runs only while the user is logged on (no password is stored), also on battery and without stopping when the laptop goes onto battery. A missed start (laptop off or asleep) runs as soon as possible. A new start is ignored while one is running, and Windows stops a run after 1 hour. `-Remove` takes the task away (it says plainly when none is installed, and a real failure stops with an error); installing again replaces it. **Not installed yet:** it is registered on the laptop after this change is merged, with the founder's separate yes. So far the script has been checked, not run: it parses, its settings objects were built and read back in memory, and `pythonw` ran `fetch --due` with no window; registering it is its real test. **The task runs whatever code is in the project folder** every 30 minutes against the real database, so the folder stays on `main` while the timer is on; to try anything else, remove the task first (`-Remove`).
- **One timer check (`fetch --due`)**:
  1. Open the database (the first ever run imports sources and topics, as `fetch` always did).
  2. Pick the due sources (below). Nothing due: write a `nothing_due` diary row and a log line, print "Nothing is due yet.", exit 0.
  3. Take the run lock (`fetch.lock` beside the database). If another fetch holds it: write a `busy` row and a log line, exit 0. (`fetch --all` and `--source` stop with an error instead and write no row.)
  4. Write a diary row marked `running`, then run `pipeline.run_fetch` with the same `now` stamp that its `fetch_runs` rows get, so the diary and the fetch history join on time.
  5. Close the diary row: `ok` or `offline`, with sources ok / failed / skipped, new items and Google refusals. Any error closes it as `failed` with the reason, writes the traceback to the log and exits 1; Ctrl+C closes it as `failed` too. Only a hard kill (power cut, killed process) leaves a row at `running`.
  - A check that fails before a run can start (an unreadable `schedule.yaml`, a database that stays locked for 30 s) writes a one-shot `failed` row if the database answers, so `status` does not mistake it for the laptop being off. The log line is always written first. The diary rows for a quiet check (`nothing_due`, `busy`) and the row that closes a run are best-effort: a database error there becomes a `warning` line in the log and never hides the result. The opening `running` row (`start_engine_run`) is not: if the database refuses it, nothing is fetched and the check ends as "could not start" (exit 1) with a log line and, if the database answers, a `failed` row.
  - `fetch --all` and `fetch --source` write the same diary rows and log line (mode `all` / `source`). Exactly one of `--all`, `--source`, `--due` is required.
- **The due rule** - a source's last attempt is the latest `fetch_runs.started_at` for it, whatever the status (a source whose only fetches failed counts as attempted). It is due if it was never attempted, or if `now - last >= interval - early`. `never` is never due; inactive sources are not considered. So a sleeping laptop costs one catch-up run: at the next check every overdue source is due once, then each goes back to its own speed. With the 30-minute beat, Telegram is fetched at every check, the 2 h sources at every 4th, the 6 h page monitors at every 12th. `last_attempted(conn, now)` ignores fetch stamps dated after `now` (the laptop's clock was wrong at that moment); counting them would make a source due at every check until real time caught up. After a clock jump a source is therefore fetched once, then at its normal speed.
- **Offline rule** (`pipeline.looks_offline`) - the run counts as offline when every source it tried (anything not `skipped`) failed to reach its site (`error_kind` timeout, dns, connect or domain_down) **and** those sources span two or more sites. One unreachable site alone is that site's problem. An offline run returns right after fetching: nothing is cleaned, grouped or tagged, no `fetch_runs` rows are written and no source's health columns change, so no source takes a strike (`consecutive_failures` stays as it was) and every one of them is still due at the next check. The diary row says `offline`; `fetch` prints "No internet". **Known limit:** a check where only the three Telegram sources (S016, S101, S102; one site, t.me) are due cannot be recognised as offline. If the internet is down then, each of the three takes a strike, and after three such checks they show up under "failing 3+ runs" in `status`.
- **Google refusals** (`pipeline.google_refusals`) - Google News feed fetches (`news.google.com`) answered with HTTP 403 or 429: the first sign of the block that D-004 accepts the risk of. (The HTTP client's `blocked` kind only means a link to X, Instagram or WhatsApp was refused, so it never applies to Google.) Counted for every run, offline ones included, stored on the diary row, and printed as a warning by `fetch` and `status`. Link look-ups are not counted. The engine never reacts by itself; a person decides what to do (a block is not undone by reverting code).
- **`engine.log`** - one line per check, appended in `data/engine.log` (beside the database, like `fetch.lock`, not in a separate logs folder, so a test database in a temporary folder never writes into the real log): IST time, mode, outcome, then due / ok / failed / skipped counts, new items, Google refusals and minutes taken (a `nothing_due` check has only the outcome; a `busy` one adds how many sources were due). A traceback goes under a `failed` line, and a `warning` line records schedule problems and diary rows that could not be written. Windows' timer runs the engine with no window, so the log and `status` are how anyone sees what happened. Writing the log is best-effort: if the file cannot be written, the line is skipped and the diary row (the other trace) is still kept.
- **`status`** (`runstatus.py`; writes nothing to the diary or the data, and only tries the run lock for an instant) prints:
  - *Last run:* the latest run that fetched or tried to (checks with nothing due, or skipped as busy, do not count): when (IST), how long ago, mode, outcome and its counts, or the reason it failed. A row still marked `running` is "running now" if a fetch holds the run lock at this moment, and otherwise "did not finish (stopped or crashed)".
  - *Last 24 hours:* the number of checks by outcome; the longest gap with no check at all (flagged if over 45 minutes, otherwise "No gaps"; with `timer: off` (D-009) a long gap is shown as "between fetches" with "fetching is by hand for now", and a short one gives just "Fetching is by hand for now, D-009." instead of "No gaps", which would claim timer checks), measured from the end of one check to the start of the next, so a long run is not mistaken for the laptop being off, and counted from the later of 24 hours ago and the first diary row, so a diary only an hour old does not claim 23 hours of silence; a warning if any diary rows are dated in the future (the laptop's clock jumped, so the times may be wrong); and the Google refusals total, with a warning if above 0. No checks at all in 24 hours is said plainly.
  - With `timer: off` in `config/schedule.yaml` (D-009: fetching by hand), a day with no checks reads "no fetches - fetching is by hand for now", and a long silence reads "Longest gap between fetches" with no warning. A missing `timer` key means on, and anything but on or off stops with a message naming the file. A diary holding only checks that found nothing due says so, rather than "no runs yet". Counts of one are singular ("1 check").
  - *Sources failing 3+ runs in a row* (active sources only), with id, name, count and last status; then any speed problems from `schedule.yaml`. With no run in the diary yet (checks that found nothing due do not count as runs) it says so and how to start one.

## Outputs (as built, 5 Oct 2026)

Why it exists: the content team and the founder need one set of files per run - the ranked stories, what moved per topic, which High-priority topics went quiet and which feeds are broken - and the four health columns to paste into the source sheet (BRIEF.md "Daily report", step 8). There is no timer (D-009), so the files are made by hand after a fetch. D-012 records the window and the before-the-AI-pass choices.

- **Commands** - `digest [--date YYYY-MM-DD] [--out reports] [--top 30] [--db] [--schedule]` writes all four files; `report [--date] [--out] [--db] [--schedule]` writes the two health files only. Files go in `<out>/<IST date>/` and a rerun overwrites them. Both refuse a missing database (never creating an empty one), a `--date` that is not `YYYY-MM-DD` or lies after today (IST), and `--top` outside 1-2,000; `digest` on a database with no articles says to fetch first, and `report` on one with no sources says to import them. Both only read: no row is written or changed (a test compares every table's row count).
- **The window** (`outputs/queries.py`, `window_for`) - by default the 24 hours before the command is run, `[now - 24 h, now)`, filed under today's IST date; with `--date` the 24 hours ending 07:00 IST that day. A story is in the window when at least one of its reports' `items.fetched_at` is in it (indexed; not `story_clusters.updated_at`, which is unindexed and rewritten whenever a story grows). Times are compared as the stored UTC ISO text (`connection.utc_iso`).
- **Queries** (`outputs/queries.py`) - every statement is a SELECT with `?` values, and every list is bounded (a LIMIT, or one row per topic or source); nothing in `db/` changed. A story's topics follow the scoring rule of `store.story_facts`: the AI's tags if the AI has tagged it, else the keyword pass's. `counts` (items fetched in the window; stories touched, new ones by `first_seen_at`, labels, stories with no AI tag), `ranked_stories` (Drop left out; ordered by score, then sources, then newest; link = the first report's URL, preferring one resolved to the publisher; source names from the story's `sources` list, in source_id order), `story_topics`, `topics_moved` (topics with a non-Drop story in the window, the count and the best headline; High priority first), `quiet_high_topics` (High-priority topics with no story that began in the 7 days before the window's end, with when one last began; one index lookup per topic), `history_start` (the earlier of the first diary row and the first fetched item), `source_health`, and `tagged_stories_by_source` (distinct topic-tagged stories per source over a period, for "Useful").
- **digest.md** (`outputs/digest.py`) - the title with the IST window; one line on the AI pass ("not run for N of M stories. Their scores leave out up to 25 points", the points read from `config/scoring.yaml`); the counts (items, stories, new, High / Medium / Low / Drop); **Top stories**, a table of the best `--top` (rank, score, label, topics, sources (first three names, then "+N more"), linked headline, debate angle, flags `sensitive` / `awaiting AI`); **Topics with new developments**; **High-priority topics with nothing for 7+ days** ("no story yet" or the day the last one began), with a "History starts ..." line while the engine has under 7 days of history. Drop stories are counted, never listed. Table cells have `|` escaped and line breaks removed, and link URLs have `|`, spaces and brackets percent-encoded, so headlines and the `|`-separated angles in `topics.csv` cannot break the table. A window with no fetched articles says so and how to fetch.
- **The debate angle before the AI pass** (D-012) - the `debate_angles` of the story's best topic (the one it scores by: highest priority + geography points, `Scorer`), always written "topic angle, not this story (O06): ...". "What's new" is "awaiting AI pass" for a story with no AI tag and empty otherwise (the AI pass's own what's new and angle are not stored yet; they come with the AI pass).
- **digest.csv** - every non-Drop story in the window, best first, at most 2,000: `rank, score, label, topics, source_count, sources, headline, url, sensitive, ai_checked, whats_new, debate_angle` (yes/no flags; all source names). UTF-8 with a BOM, so Excel shows Kannada.
- **health.md** (`outputs/health_report.py`) - always as of the moment it is made (source health has no history; a past `--date` says so). *Engine*: the same lines `status` prints (`runstatus.report`, with the run-lock check, plus speed problems from `config/schedule.yaml`; the CLI shares one helper). *Sources*: a count per group and "Passing health checks: N of M non-X sources (target 90%)", then each group listed. Every active source is in exactly one group, in this order: manual (`Manual` route); never fetched; skipped (input gaps such as S047, S107, S108, S121); failing 3+ runs in a row (`consecutive_failures`, flagged for replacement); failed the last run (1-2 in a row); stale (newest item older than 7 days, `health.STALE_AFTER`; page monitors 30 days, `health.PAGE_STALE_AFTER`; a feed with no dated item yet; a page monitor that has not changed yet is not stale); working. *Not useful* (BRIEF.md: 0 topic-tagged items in 7 days, flagged for replacement) is checked on working and stale sources, with a "History starts ..." line while there are under 7 days of history. *Blocklist*: `Blocklist.problems` (rows with no domain), or that every row is applied.
- **sources_health.csv** - `source_id, name, last_status, last_ok_at, newest_item_at, fields_present`, one row per active source in source_id order, times as `YYYY-MM-DD HH:MM` IST, UTF-8 with a BOM: the four columns BRIEF.md says to paste into the source sheet.
- **Not built:** the 07:00 run itself (no timer, D-009), the dashboard pages and `/api/stories`; the AI pass's own "what's new" and debate angle.

## Ground-truth log (as built, 5 Oct 2026)

Why it exists: the recall test (step 10) scores every source against the editor's log, and the editor logs from day 1 of the two-week test, before matching is built. So the format and its checks come first.

- **The file** - `data/ground_truth.csv` (gitignored, on the laptop), kept by the editor in Excel or Google Sheets. The columns are `date, topic_id, what_happened, where_seen, time_seen` (BRIEF.md step 10). Headers are read case-insensitively, with spaces read as `_`. Extra columns are ignored. Files are written as UTF-8 with a BOM, because Excel needs it to show Kannada, and read with or without one. A file that is not UTF-8 is refused, with how to save it.
- **Reading** - `groundtruth.read_log(path, topics, now)` returns `entries` (`row`, `seen_at` as aware IST, `topic_id` upper-cased, `what_happened`, `where_seen`), `errors` and `warnings`, each naming its spreadsheet row.
  - Accepted dates: `YYYY-MM-DD`, `DD-MM-YYYY`, `DD/MM/YYYY` (Excel's Indian style).
  - Accepted times: `HH:MM`, `HH:MM:SS`, `9:15 AM`.
  - Errors leave the row out: an empty cell, an unreadable date or time, an unknown topic id, or a moment in the future.
  - Warnings keep the row: a topic that is not High priority; or the same day, topic and development (case and spacing ignored) as an earlier row, which counts once.
  - Blank rows are skipped. Step 10's import and nightly match read the log through this function; the planned `ground_truth` table maps `date` + `time_seen` to `seen_at`.
- **Commands** - `log-template` writes the header-only log, never over an existing one, and rewrites `data/ground_truth_topics.csv` (the High-priority topics, from `topics.csv`). `check-log` prints `Fix:` and `Note:` lines and a count, and exits 1 while any row has an error.

## Data model (as built, 4 Oct 2026; engine_runs added 5 Oct 2026)

One SQLite file, `<project>/data/engine.db` (or `RIFFI_DB_PATH`), anchored on the project folder rather than the current folder (Windows Task Scheduler starts in System32), refused inside OneDrive (D-001); WAL, foreign keys on, 30 s busy timeout. Every date is ISO-8601 in UTC, so text order is time order. Tables (`riffi_ingest/db/schema.py`):

- **sources** - feeds.csv columns + `active` + health columns kept by every fetch: `last_status`, `last_ok_at`, `newest_item_at`, `fields_present`, `consecutive_failures`, and the conditional-GET `etag` / `last_modified`.
- **fetch_runs** - one row per source per run: status (ok / not_modified / skipped / error), `http_status`, `duration_ms`, `items_returned`, `newest_item_at`, `fields_present`, `on_backup`, `error`. Indexed on (source_id, started_at).
- **items** - the BRIEF.md items shape plus `canonical_url`, `url_resolved`, `on_backup`, `cluster_id`. `raw_payload` (JSON) is cleared after 30 days (D-002). Indexed on published_at, fetched_at, cluster_id, canonical_url.
- **story_clusters** - `headline`, `first_seen_at`, `started_at` (first report; the 48 h window's anchor), `source_count`, `publisher_count`, `sources` (JSON), `page_monitor`, `unmatched_local`, and `relevance_score` / `label` / `sensitive` for step 5.
- **item_topics** - (cluster_id, topic_id, match_method keyword|llm), `confidence`, `evidence` (matched keywords as JSON, or the AI's reason). Keyword rows are recomputed from the whole story each run; llm rows are never touched by the keyword pass.
- **page_snapshots** - every page-monitor snapshot; `text` cleared after 30 days except each page's latest (the next comparison needs it).
- **ground_truth** - the editor's log: `logged_on`, `topic_id`, `what_happened`, `where_seen`, `seen_at` (step 10).
- **engine_runs** - the run diary (5 Oct 2026, D-008): one row per fetch run and per timer check that fetched nothing, about 48 a day, kept forever as test evidence. Columns: `engine_run_id`, `started_at` (a run's is the same stamp as its `fetch_runs.started_at`), `finished_at` (empty while running, or if the run never finished), `mode` (`due` = the timer, `all`, `source`), `outcome`, `sources_due`, `sources_ok`, `sources_failed`, `sources_skipped`, `items_new`, `google_refusals`, `error`. Outcomes: `running` (started, not closed), `ok`, `offline` (no internet; blamed on no source), `failed` (with the reason in `error`; also the one-shot row for a check that failed before a run could start), `nothing_due` and `busy` (one-shot rows: a check that fetched nothing, or found another run holding the lock). Indexed on `started_at`. Modes and outcomes are free text in the table, so `db/store.py` checks them against fixed lists before writing (`start_engine_run`, `finish_engine_run`, `log_engine_tick`); `finish_engine_run` closes a row only while it is still `running` and raises otherwise, so the diary never says something that did not happen. Added with `CREATE TABLE IF NOT EXISTS`, so an existing `engine.db` gains it on the next connect with its data untouched (`schema_version` stays 1). Also in `db/store.py`: `last_attempted(conn, now)`, `engine_runs_since`, `last_engine_run`, `first_engine_run_at`, `failing_sources`.
- Helpers: **topics** (topics.csv), **gnews_cache** (Google News article id -> publisher URL, so a link is resolved once ever), **schema_version** (one row; a newer file is refused, never overwritten).

`db/importers.py` seeds sources and topics; re-importing updates rows in place, keeps health columns and history, and marks a source that left feeds.csv `active = 0` (never deleted). `db/store.py` records each fetch, loads validators / page snapshots / the Google News cache / the last 48 h of stories, saves a run's items and stories in one transaction (an item already stored keeps its story; a story is written only when it gains a new item; counts and sources are recomputed from stored items, so an old article listed again never shrinks or duplicates a story), saves keyword tags, and prunes. Nothing deletes rows; SQL statements are fixed text with `?` values only.
